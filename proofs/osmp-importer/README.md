# OSMP binary variables at the Importer edge (#244)

```sh
proofs/osmp-importer/run-proof.sh [output-directory]   # default build/osmp-importer
```

This proves the OSMP mapping of the FMI 2.0 profile
([docs/fmi.md](../../docs/fmi.md#osmp-binary-variables)) on its named
consumer: `OSMPDummySource` drives `OSMPDummySensor` from
osi-sensor-model-packaging `v1.6.0`, selected in
[#230](../../docs/decisions/230-external-adas-targets.md).

The image build is the only step that uses the network. It fetches the OSMP
checkout pinned in [`../osmp-sensor/sources.json`](../osmp-sensor/sources.json)
and builds both FMUs exactly as [`../osmp-sensor`](../osmp-sensor/) does.
Everything else runs with `--network none` on Linux x86-64 and writes
`evidence/report.json`.

A check that fails stops the proof, so a failed check cannot write a passing
report. `.github/workflows/proof-osmp-importer.yml` runs the proof on native
Linux x86-64 and uploads `evidence/`.

## Run

Each FMU runs in its own Process participant, `python -m sil.fmi`. Two of
these FMUs cannot share one process
([One process](../osmp-sensor/README.md#one-process)), and an OSMP address is
valid only in its own process. So the SensorView crosses on a Channel as
bytes:

| Channel | Publisher → subscriber | Schema | Latency |
| --- | --- | --- | --- |
| `osi.SensorView` | source `OSMPSensorViewOut` → sensor `OSMPSensorViewIn` | `payload` `u8[4096]`, `payload_length` `u32` | 0 |
| `osi.SensorData` | sensor `OSMPSensorDataOut` | `payload` `u8[4096]`, `payload_length` `u32` | default |
| `sensor.Status` | sensor `valid`, `count` | `u8`, `i32` | default |

Period 20 ms (the sensor's configuration request), 1500 Steps (30 s), source
priority 0, sensor priority 1. The source publishes in the Slot at `t` the
SensorView of `t + 20 ms`, the end of its Step. With Latency 0 the sensor,
ordered after it, steps over `[t, t + 20 ms]` with that SensorView, so it
consumes the ground truth of the instant its own Step ends at. This is the
freshness of the #230 expected slice.

The expected values are computed at the times the FMUs compute. The Importer
gives `fmi2DoStep` the communication point `t / 1e9` and the step
`0.02`, each made from integer nanoseconds. Both FMUs stamp their output with
the sum of these two doubles, truncated to whole nanoseconds. For example,
`0.18 + 0.02` is `0.19999999999999998`, which gives the timestamp
`0 s 199999999 ns`. #230 drove FMPy at `k · 0.02`, and that double is
different at 201 of the 1500 Steps. So the proof computes the slice of
`scene.py` again at the Importer's own communication points. It does not use
the slice that #230 wrote.

The Importer moves bytes only. The proof decodes the recorded payloads with
Python classes generated by `protoc` from the same `.proto` files the FMUs
were built from.

## Checks

| Check | Requirement |
| --- | --- |
| Inspection | `sil-fmi-inspect` reports both archives `compatible`, lists their OSMP binary variables and accepts the mappings the Runs use |
| SensorView | every recorded SensorView equals the closed-form source motion (`proofs/osmp-sensor/drive.py`, 1e-9) |
| SensorData | every recorded SensorData equals the expected slice of `proofs/osmp-sensor/scene.py` (default `nominalrange` 135 m): the same vehicles in the same order, tracking ids, timestamps, and each pose, dimension and existence probability to 1e-9. `valid` is 1 and `count` is the number of objects |
| Identity | the Run twice: the two Recordings are byte-identical |
| Late connection | with the default Latency on `osi.SensorView`, the sensor sees each SensorView one Period late and its first Step none. The comparison must fail |
| Size error | with `osi.SensorData` bound to 1024 bytes, below the smallest SensorData of the nominal Run, the Run fails with exit 1 and the diagnostic names `OSMPSensorDataOut` and the bound |
| Cleanup | nothing is left in the runner's directory after any Run |

The FMU binaries are compared with the #230 pins in `report.json` → `build`.
That is reported, not required: #230 found the rebuild identical.
